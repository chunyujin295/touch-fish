一次线上事故，让我重新理解了内存屏障

原创 云舟的技术笔记 · 2026-10-28 21:14 · 上海

上周三凌晨两点，我们的服务在扩容到 8 核之后，开始出现一种很难解释的现象：某个接口每小时会有两三次返回错误的数据，重启之后又好了，压测的时候怎么都复现不出来。

排查了两天，最后定位到一行看起来完全正确的代码。这事让我重新把内存模型翻了一遍，也让我意识到：我们平时写的并发代码，很多只是"看起来对"。

一、顺序是一种局部共识

我们习惯把程序看成一条按顺序执行的指令流：先算 A，再算 B，最后写 C。先发生的事一定先发生——这句话在单核时代几乎是不证自明的。

但把视角从单核挪到多核，"顺序"就开始松动了。它并没有消失，只是从客观事实变成了局部共识：每个核都以为自己看到了正确的顺序，而它们看到的顺序可以互不相同。

一个程序如果只在单线程下被验证过，那么它对"正确"的证明就只覆盖了所有可能执行的交错中的一小部分。

硬件做了两件事，而且它们互相配合：一是每个核都有自己的 store buffer 和 invalidate queue；二是允许在不改变单线程语义的前提下对指令重排。这两件事合起来，就是所有内存模型问题的源头。

// 生产者线程 data = 42; ready = 1; // 消费者线程 while (!ready) { /* spin */ } assert(data == 42); // 有可能失败

很多人第一次看到这个例子的反应是"编译器优化了吧"。把 -O2 关掉，加上 volatile，问题照旧。因为重排不只发生在编译器，也发生在 CPU 的乱序执行单元和缓存一致性协议之间。

二、那个"每周崩一次"的 bug

这类问题有一个非常稳定的特征：它在单线程压测里跑一万次都正确，在多核机器上每周崩一次；日志里没有异常，core dump 里变量值看起来"完全正常"。

它不偶发，它是必然，只是在等一个足够坏的时序。

  • 复现条件苛刻：需要两个核同时进入临界窗口，且其中一个恰好被中断或迁移；
  • 加日志即消失：因为日志引入了屏障，时序被"治好"了——这也是最迷惑人的地方；
  • 修复成本极低，定位成本极高：最后往往只是补一个 std::atomic 的 acquire/release 语义。

三、写进工程习惯

理解内存模型之后，落到工程上其实只有很少几条可执行的规则：共享状态默认不可变；可变共享状态一律走同步原语，不要靠"我觉得这里不会重排"；任何时候看到 if (flag) 去读另一份数据，都停下来想一秒。

真正需要建立的直觉不是"记住 MESI 的四个状态"，而是：任何跨线程共享的可变状态，都必须显式地建立 happens-before 关系。

编译器与硬件只对单线程负责，跨线程的顺序需要你自己付钱。
