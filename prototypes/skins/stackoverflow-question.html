Why does this cache visibility assertion fail on multi-core?

Asked 2 days ago · Modified yesterday · Viewed 4,281 times
12

Environment: 4-core x86_64, Linux 6.1, compiled with -O2. The snippet below runs correctly ten thousand times in a single-threaded stress test, but on a multi-core machine the assertion fails roughly once a week. In the core dump, data is exactly 0.

// producer thread
data = 42;
ready = 1;

// consumer thread
while (!ready) { /* spin */ }
assert(data == 42);   // fails sometimes

My first guess was that the compiler was optimising away the read. I added volatile to both variables, and I also inserted a printf between the two sides. The result was confusing: with the logging in place, the bug disappeared. Without it, the failure comes back within a week.

So is this compiler reordering, or is it a visibility problem caused by the store buffer? And if it is the latter, why doesn't volatile fix it?

It's the latter — and to be precise, it's both layers at once. Let me separate them.

1. Ordering is a local consensus

Each core believes it observed the correct order, but different cores can observe different orders. The hardware does two related things: every core gets its own store buffer and invalidate queue, and it is allowed to reorder instructions as long as single-threaded semantics are preserved.

A program that was only verified single-threaded has proved correctness for a small subset of all possible interleavings.

In your case, ready = 1 can become visible to the other core before data = 42 does. Once the store sits in the store buffer it "looks finished" locally, but it has not reached the cache line yet.

2. Why volatile does not help

  • volatile guarantees the access is not optimised away and really happens — it does not establish an ordering that other cores must observe;
  • printf happens to act as a barrier (it takes a lock / makes a syscall), which is exactly why the symptom "heals" itself when you add logging. Do not trust that observation;
  • the correct fix is a release store paired with an acquire load, so that publishing the flag carries the data with it.
std::atomic<bool> ready{false};

// producer
data = 42;
ready.store(true, std::memory_order_release);

// consumer
while (!ready.load(std::memory_order_acquire)) {}
assert(data == 42);   // now guaranteed

One more thing worth internalising: the bug is not intermittent, it is deterministic — it is simply waiting for a sufficiently bad interleaving. "Once a week under production load" is the normal shape of this class of bug.

Adding to the accepted answer: if data is a struct, making every field atomic is not enough. You still need one publication step for the whole object, otherwise a reader can observe a half-updated struct (torn read).

Either put the entire struct behind one lock, or publish it through a single atomic pointer with release/acquire semantics.
