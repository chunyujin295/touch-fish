先说明一下环境：4 核 x86_64，内核 6.1，用 -O2 编译。下面这段代码在单线程压测里跑一万次都正确，但部署到多核机器之后大约每周崩一次，assert 失败，core dump 里 data 恰好是 0。

// producer
data = 42;
ready = 1;

// consumer
while (!ready) { /* spin */ }
assert(data == 42);   // fails sometimes

我最初判断是编译器优化掉了读操作，于是把 volatile 加上，还在两个线程之间插了 printf。结果很奇怪：加了日志之后，问题就消失了，去掉日志一周后必然重现。

问题：这到底是编译器重排，还是 CPU 层面的 store buffer 导致的可见性问题？如果是后者，为什么 volatile 不管用？

是后者，而且两者都有。分两层说。

1. 顺序是局部共识

每个核都以为自己看到了正确的顺序，但不同核看到的顺序可以互不相同。硬件做了两件互相关联的事：每个核有自己的 store buffer 与 invalidate queue；并且允许在不破坏单线程语义的前提下重排指令。

一个只在单线程下验证过的程序，它对"正确"的证明只覆盖了所有可能交错中的一小部分。

在你的例子里，生产者的 ready = 1 可能先于 data = 42 对其他核可见——写操作进了 store buffer 就"看起来完成了"，但还没落到缓存行。

2. 为什么 volatile 不管用

  • volatile 保证的是"不被优化掉、每次都真的读写"，不是"对其他核的可见顺序"；
  • printf 恰好起到了屏障作用（内部有锁/系统调用），所以现象"被治好"了——这是最迷惑人的地方；
  • 正确的做法是用 std::atomic 的 release/acquire，把数据写入与标志位发布串起来。
std::atomic<bool> ready{false};

// producer
data = 42;
ready.store(true, std::memory_order_release);

// consumer
while (!ready.load(std::memory_order_acquire)) {}
assert(data == 42);   // now guaranteed

顺带一提，你这句"每周崩一次"的描述很典型：它不是偶发，是必然，只是在等一个足够坏的时序。

补充一个我们线上踩过的坑：这类 bug 还有一个特征是加日志即消失，因为日志本身引入了屏障，时序被"治好"了。所以排查时千万别用打日志的方式验证，你会把现场毁掉。

后来我们的规范是：任何跨线程共享的可变状态，必须显式建立 happens-before 关系，Review 时看到 if (flag) 去读另一份数据就拦下来。
