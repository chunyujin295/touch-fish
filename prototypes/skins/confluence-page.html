缓存一致性排查手册（值班版）

张
张伟 创建于 2026-10-21 · 最后修改 2 小时前 · 218 次浏览
i 值班须知
本页为一线排查手册，遇到疑似缓存一致性问题时按顺序执行，不要跳过第 2 步。

线上出现"偶发数据不一致"时，第一反应通常是怀疑缓存没刷新、DB 主从延迟或者消息重复消费。但在多核环境下，有一类问题既不在缓存中间件，也不在数据库，而在程序自己的内存可见性上。

本文记录一次真实事故的排查路径与结论，供值班同学参考。

一、现象与判断

最典型的特征：单线程压测跑一万次都正确，上到多核机器后每小时出现几次错误，重启可暂时缓解，日志里没有任何异常堆栈。

! 注意
排查期间不要用打日志的方式验证。日志本身会引入内存屏障，问题会"消失"，现场被破坏后极难复现。

下面这段代码是最小复现，几乎每一本讲并发的书都会引用：

cpp复制
// 生产者线程
data = 42;
ready = 1;

// 消费者线程
while (!ready) { /* spin */ }
assert(data == 42);   // 有可能失败

关掉 -O2、加上 volatile，问题照旧。因为重排不只发生在编译器，也发生在 CPU 的乱序执行单元和缓存一致性协议之间。volatile 保证的是"不被优化掉"，不是"对其它核可见的顺序"。

二、快速对照表

现象可能原因验证方式
多核偶发、单核必现不了store buffer 重排 / 缺少屏障加 std::atomic release/acquire 后压测 72h
加日志后消失日志引入了隐式屏障改用不带 I/O 的断言与计数器
低负载正常、高负载劣化伪共享（false sharing）perf c2c 看缓存行争用
读到的结构体字段只更新了一半撕裂读（torn read）整对象单次发布，或加锁

三、处置步骤

  1. 确认机型与并发度：单核能复现的，先怀疑逻辑 bug，不要往内存模型上带。
  2. 定位共享可变状态：把跨线程读写的字段全部列出来，标出哪一处是"发布标志位"。
  3. 建立 happens-before：发布用 release store，读取用 acquire load，不要用 volatile 凑。
  4. 压测 72 小时：低于这个时长不算验证通过。

需要建立的直觉不是"记住 MESI 的四个状态"，而是：任何跨线程共享的可变状态，都必须显式地建立 happens-before 关系。编译器与硬件只对单线程负责，跨线程的顺序需要你自己付钱。
